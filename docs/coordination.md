# 项目协调约定

本对话作为项目起点与协调站，负责统筹范围、拆分任务、安排验收、收回执行证据、处理阻塞并决定下一步。专项实现可以由有边界的执行任务推进，结果需回到协调站核查后进入项目进度。

## 共同观察入口

进度事实以 `progress/project-status.json` 为唯一来源；交互 HTML 看板和 `docs/state.md` 由它生成。仓库保存可追溯版本，私有 Sites 看板提供固定查看地址；站点身份和发布信息保存在忽略的 `.local/coordination-site/` 与 `.local/coordination-site.json`。

看板显示当前焦点、阶段依赖、任务验收数量、证据、阻塞和最近事件。任务数不等于工时权重，不展示笼统的项目完成百分比。页面上的筛选与展开只改变视图，不会把任务标成完成。

## 状态含义

| 状态 | 含义 |
|---|---|
| `planned` 待开始 | 已有目标，尚未进入当前执行队列 |
| `ready` 可开始 | 前置任务已验收，下一动作明确 |
| `active` 进行中 | 本轮正在推进，验收尚未完成 |
| `blocked` 有阻塞 | 有具体的外部或技术条件阻止推进，并记录下一动作 |
| `done` 已验收 | 满足验收条件并链接到代码、测试、记录或交付物 |

依赖未验收的任务不能标为 ready/active/done。完成任务必须有证据。历史阻塞保留为事件，当前阻塞只反映仍存在的条件。

阶段已有任务验收、但尚未全部完成时显示“部分验收”；所有定义任务都完成后，将 `focus_task` 设为 `null`，看板进入验收完成状态。事件按时间倒序生成，追加记录不会使两个视图显示不同的最新进展。

## 每次工作结束的更新

1. 开始前读取进度源、当前状态、相关方案及 Git 工作区，确定这次推进的任务与验收门槛。
2. 执行任务并保留实际证据。原生环境验证、调度正确性与性能结论分别验收。
3. 核查结果后修改进度 JSON，更新状态、证据、阻塞、下一动作与事件；不要只改生成的页面。
4. 执行 `make progress` 和 `make check`。CI 会检查生成文件是否与数据一致。
5. 提交并同步 GitHub；更新集群 checkout 时使用 `git pull --ff-only`，保留忽略的环境与数据。
6. 将生成 HTML 同步到现有私有 Site 的 `dist/index.html`，按 Sites 固定 project_id 保存并发布，确认部署成功。
7. 在本对话简要报告本次变化、未解决条件和下一张任务卡。

更新节奏为每次项目工作结束以及阶段验收时。固定网页显示最近一次已核查的快照，不自动推断后台服务器状态。需要无人值守、定时检查或主动通知时，再单独约定频率、数据来源与通知条件。

## 协调与执行边界

协调站维护依赖关系和验收事实；执行任务按给定范围修改代码并返回结果；用户决定方向、资源与关键取舍。当前核心技术方向保持不变：先原生 B/C 反例，再小窗口排序与等待保护，再原生回归和单卡实验。

远程连接先通过 Cisco Secure Client 连学校 VPN，再进行 SSH。VPN 密码、学校账号、主机、内部地址和真实资源路径不进入进度数据或公开看板，保存在本机忽略配置中。每次作业使用明确时限，结束确认引擎退出和分配释放。

技术范围、模型、后端、Graph 或测量定义发生变化时，先记录决策和对照影响，再更新任务与基线。不得用已有机制或功能冒烟结果替代个人实现、原生正确性或性能证据。
