# 项目方案与验收

## 目标

在 vLLM 0.32.0 中独立实现共享前缀感知的小窗口请求重排，并增加等待保护。通过原生 Scheduler replay 和单卡实验证明执行顺序的变化、实际 prefill 工作量的变化，以及冷热请求各自承担的等待代价。

采用成熟机制的独立实现与框架适配，工程扩展限定为等待保护。优化是否成立由对照实验决定，不预设必须额外加速 10%。

## 机制场景

1. 前缀 A 的 KV 已缓存并可被复用。
2. 冷请求 B 先到达，稍后的请求 C 可以复用 A。
3. 原生 FCFS 先准入 B；其分配可能淘汰 A，导致 C 重新 prefill。
4. 窗口排序尝试先执行 C，在 B 分配前复用 A。
5. 持续热流量下加入等待保护，观察冷请求是否持续被越过。

该场景需要真实缓存压力和候选队列。当前 2,230-token 重复提示的原生验证只证明 APC 能命中，尚未构成 B/C 淘汰反例。

## 三种模式

默认 `mode=off`、`window=16`、`max_wait_ms=500`；配置契约记录在 `configs/scheduler-plan.json`，M3已实际接入真实异步引擎；完整验收仍受历史资源证据缺口阻断，见[M3交接](research/m3-handoff.md)。

- `off`：保留原生调度顺序，用于和原生类做扩展成本与等价性对照。
- `prefix`：窗口候选按当前可复用前缀 token 数降序排列，同分保持原始顺序。
- `guarded`：进入等待保护的候选先按原始到达顺序排列，其余候选再按前缀命中排序。

保护只承诺窗口内排序行为：候选进入保护后，更新的热请求不能在该次候选窗口内越过它。过载、资源不足和窗口外等待仍可能使 TTFT 超过阈值。

## 必须保持的边界

只取队头连续、尚未开始计算的普通 `WAITING` 请求；遇到 blocked、恢复或部分计算请求立即停止，不跨屏障。窗口操作应为局部取出与恢复，不全队列过滤后再截断。每个调度 step 最多排序一次，再调用原生调度。

只读评分使用原生 hash 与查找路径，不分配 KV blocks，不改变引用、缓存映射和 free queue，不污染统计或产生虚假的 `BlockStored` 事件。首版每次重新评分，不引入跨 step memo。

等待时间由独立的单调时钟元数据记录。取消、完成等终止路径要清理元数据，并检查请求 ID 复用。原生异步占位、抢占、KV 分配和模型执行保持；不兼容的全局配置在启动时拒绝，运行时非候选请求由原生路径处理。

## 验证与交付

先做真实 Scheduler replay，检查 B/C 的实际准入顺序与 prefill tokens，然后完成三种模式与只读探测，再进入真实模型闭环。

原生回归至少覆盖关闭等价、热请求提升、同分 FIFO、窗口边界、blocked/部分计算屏障、全冷、APC 关闭、窗口 1、多个受保护请求、评分无副作用、取消/完成/抢占/ID 复用、异步占位、资源释放与队列恢复。特别检查 `extendleft` 对恢复顺序的反转。

正式实验详见 [实验规范](experiments.md)。工程验收与性能结论分开：前者要求真实引擎扩展可运行、回归通过、资源正确清理并可重放；后者说明减少了多少 prefill、端到端表现如何变化、代价落在哪些请求上。

最终展示执行前后图、请求时间线、prefill/重算工作量图、性能与公平性图，以及一条失败用例到实现再到重放命令的代码演示。所有图应从同一份原始 trace 生成，不建设通用监控平台。
